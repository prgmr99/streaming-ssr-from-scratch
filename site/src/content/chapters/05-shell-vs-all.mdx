## 콜백이 두 종류인 이유

2장에서 `renderToPipeableStream`이 콜백을 받는다고 했습니다.
그중 완성 시점을 알려주는 것이 두 개 있습니다.

| 콜백           | 호출 시점                              |
| -------------- | -------------------------------------- |
| `onShellReady` | Suspense **바깥** 영역이 완성됐을 때   |
| `onAllReady`   | **모든** Suspense 내부까지 완성됐을 때 |

지금까지는 `onShellReady`를 썼습니다.
여기서 `pipe`를 부르니 shell이 준비되는 즉시 응답이 나갔습니다.

그런데, React는 `onAllReady`도 줍니다.
여기서 `pipe`를 부르면 전부 준비된 뒤에 한 번에 나갑니다.
스트리밍의 이점이 사라집니다.

스트리밍이 좋은 것이라면, 왜 `onAllReady`가 존재하는지 궁금했습니다.

## 한 줄만 바꾼다.

```typescript
onAllReady() {
  pipe(passThrough);
},
```

위에서 설명드렸듯이 onAllReady를 사용했을 때는 직관적으로 2초뒤에 결괏값을 반환하는 getTodoList까지 완료되어야 모든 컨텐츠를 보이게 됩니다.
그렇다면, TTFB도 대략 2초대로 나올 것입니다.

## 응답에서 대부분이 사라졌다.

```html
<div id="root">
  <h1>Todo List</h1>
  <!--$-->
  <ul>
    <li>Buy groceries</li>
    ...
  </ul>
  <!--/$-->
</div>
```

이게 전부였습니다. 앞서보던 응답과 비교하면 차이가 뚜렸했습니다.

**`onShellReady`**

```html
<!--$?--><template id="B:0"></template>
<div>loading...</div>
<!--/$-->
...
<div hidden id="S:0">
  <ul>
    ...
  </ul>
</div>
<script>
  $RB=[];$RV=function(a){...};$RC=function(a,b){...};$RC("B:0","S:0")
</script>
```

**`onAllReady`**

```html
<!--$-->
<ul>
  ...
</ul>
<!--/$-->
```

사라진 코드들을 한 번 살펴보았습니다.

- `loading...` fallback 코드
- `<template id="B:0">` 자리 표시자
- `<div hidden id="S:0">` 화면 밖에 도착하던 조각
- `$RC` / `$RV` / `$RB` 교체 스크립트 전체

완성된 상태로 보내니 나중에 채운다는 표시 자체가 불필요해진 것입니다.

주석 마커도 바뀌었습니다.

|                | 마커        | 의미   |
| -------------- | ----------- | ------ |
| `onShellReady` | `<!--$?-->` | 미해결 |
| `onAllReady`   | `<!--$-->`  | 해결됨 |

## TTFB가 또 속였다.

```
TTFB: 0.013438s / Total: 2.032018s
```

2초가 나올 줄 알았는데, 0.013초가 나왔습니다.

`Content-Length`가 없는 chunked 응답이라, `Response` 객체가 만들어지는 순간 헤더와 스트림 시작 신호가 먼저 나갑니다.
curl은 그것을 첫 전송으로 계산했습니다. 실제 본문은 2초 뒤에 오는데도 말입니다.

브라우저로 열어보면 2초간 흰 화면이 명확하게 보입니다.

4장에서도 보았지만, TTFB는 스트리밍 여부를 판정하는데 쓸 수 없다고 판단이 됩니다.

믿을 수 있는 것은 두 가지입니다.

- 응답 원문에 fallback과 교체 스크립트가 있는가
- 화면에 첫 컨텐츠가 언제 뜨는가

## 그러면 onAllReady는 왜 존재하는가

|             | `onShellReady`     | `onAllReady`  |
| ----------- | ------------------ | ------------- |
| 사용자 체감 | 6ms에 `loading...` | 2초간 흰 화면 |
| 응답 크기   | 큼                 | 작음          |
| fallback    | 있음               | 없음          |
| JS 의존     | 교체에 필요        | 불필요        |

검색엔진 크롤러는 JS를 실행하지 않거나 늦게 실행합니다.
`onShellReady` 응답을 받으면 `loading...`을 컨텐츠로 인식할 수 있는 문제가 있습니다.
반면, `onAllReady`는 완성된 HTML을 전달하기 때문에 문제가 될 일은 없습니다.

정적 사이트 생성도 마찬가지입니다.
빌드 타임에 HTML 파일로 저장하는 것이 목적이니 스트리밍은 의미가 없습니다.

한 문장으로 정리하면 이렇습니다.

> `onShellReady`는 사람을 위한 것, `onALLReady`는 기계를 위한 것

사람은 2초간 흰 화면을 견디기 어렵지만 `loading...`은 참아줍니다.
크롤러는 화면을 보지 않으므로 `loading...`을 그냥 콘텐츠로 읽습니다.
